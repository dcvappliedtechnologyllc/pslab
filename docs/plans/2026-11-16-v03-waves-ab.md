# pslab v0.3 plan: waves A and B

Date 2026-11-16. Branch `v03`. Input: `docs/handoff-2026-11-15.md`.

**In scope:**
- Wave A: bugs 1, 9, 10 and 16; move_layer, reorder_layer and select_layer; `above` on copy_to, clone_from, content_aware_fill and add_pixel_layer; layer bounds, text and maskEnabled in get_document; delete_layer with `layers`.
- Wave B: add_shape, add/set/clear_layer_style, align_layers, transform_layer, set_blur, and content_aware_fill `sample`.

**Out of scope:** items 14 and 15, the batch tool, and the skill notes.

## Conventions every task follows

- **Server:** zod 4 `inputSchema`; the handler calls `forward`/`call`; `toolResult`/`toolError`. Every tool sets `annotations: hints.<profile>`.
- **New hints profile:** add `edit: hint(false, false, false)` to `server/src/tools/common.ts`, documented as "changes an existing layer relative to its current state; repeating it changes it again". It is for move_layer (dx/dy) and transform_layer.
- **Destructive set stays pinned** to crop, delete_layer, export, save, save_psd. No new tool is destructive. clear_layer_style uses `set`: it is undoable and only touches effects.
- **Array schemas:** any array is `z.array(single schema)`, never a tuple. The schema-audit test in `tool-names.test.ts` catches tuple-style `items`.
- **Either-or arguments:** two optional fields plus a check in the handler (e.g. `layer` | `layers`, `sample` + `sample_layers`). This keeps schemas simple; anyOf is legal but harder for callers to follow.
- **Plugin actions:**
- Validate before `runStep`, so a rejected call leaves no history state.
- One `runStep`/`stepIn` per call, history name `Claude: <tool>, <key values>`.
- batchPlay goes through `bp()`; the DOM is preferred where it is reliable.
- Action names in `plugin/lib/actions/index.js` must equal the MCP names.
- **New server tool files** (`server/src/tools/layers.ts`, `server/src/tools/design.ts`) must be registered in `server/src/index.ts`, `scripts/dev-harness.mjs` and both describe blocks of `server/test/tool-names.test.ts`.
- **New plugin action files** (`plugin/lib/actions/layers.js`, `plugin/lib/actions/design.js`) are registered in `actions/index.js`. Shared helpers come from `edit.js` (`codedError`, `requireLayer`, `stepIn`), which already exports them.
- **Tests:**
- Server: vitest, `FakePlugin` and an in-memory MCP client, in the style of `server/test/tools-geometry.test.ts`. Assert the forwarded args, defaults, handler-level refusals and description keywords.
- Plugin: `node --test` with a stub `ps`, plus pure-function tests.
- **Live check procedure:**
1. `npm run build -w server`.
2. Reload the plugin in the UXP Developer Tool.
3. `node scripts/dev-harness.mjs`.
4. `curl -s -XPOST localhost:9778/call -d '{"name":"<tool>","args":{...}}'`.
5. Confirm in Photoshop's History panel that the call made one named state.
6. Log the result in `docs/development-log.md` under "v0.3 wave A/B".
- **Recorded descriptors:**
1. `curl -XPOST localhost:9778/call -d '{"name":"dev_events","args":{"clear":true}}'`.
2. Do the listed steps by hand in Photoshop.
3. `dev_events` again, and copy the descriptor into `plugin/lib/recorded/<file>.js` as `module.exports = {...}`.
4. Register the file in `plugin/lib/recorded/index.js` and update `plugin/lib/recorded/README.md`.
5. Until a file exists, the tool answers NOT_SUPPORTED (same rule as today). Tasks marked **[needs recorded descriptor]** depend on this.

### A2. Modal state and MODAL_BUSY (bug 16)

**Files:**
- `plugin/lib/doc.js`
- `plugin/lib/dispatch.js`
- `plugin/main.js` (wherever the dispatcher is built)
- `plugin/lib/actions/see.js`
- `plugin/test/dispatch.test.js`, `plugin/test/see.test.js`
- `server/src/tools/see.ts` (description), `server/test/tools-see.test.ts`

**Plugin:**
- **`modalState(ps, d)` in doc.js:**
- Probe with `ps.core.executeAsModal(async () => {}, {commandName: "pslab modal probe", interactive: false, timeOut: 1})`. If it resolves, return null.
- If it throws, classify the modal:
  - `"crop"` if a layer named "Crop Preview" exists in `d`.
  - Otherwise a batchPlay `get` of the application's `tool` property (wrapped in try): `cropTool` gives "crop"; `typeCreateOrEditTool` / `typeVerticalCreateOrEditTool` give "text"; anything else gives "transform".
  - `"busy"` when the error number is 9 (another plugin holds the modal scope).
  - `"unknown"` if classification itself fails.
- **`requireNotModal(ps, d)`:** throws `MODAL_BUSY: Photoshop is in a modal state (<kind>); commit or cancel it, then retry`.
- **get_document:** calls `modalState` and returns `modal` in the summary (`null` normally).
- **Dispatcher:** `createDispatcher` gets an optional `modalState` hook. When an action fails with code NO_LAYER, NO_DOCUMENT, BATCHPLAY, MODAL_FAILED or STEP_FAILED, it probes once and rewrites the error to MODAL_BUSY with the kind. This costs nothing on the happy path and covers every tool, including tools that validate layer ids before their modal scope (the source of the NO_LAYER in the handoff).
- **No probe** inside `docSummary` for ordinary responses.

**Server:** update the get_document description to explain `modal` (non-null means the layer tree may show "Crop Preview" and a provisional width; finish or cancel in Photoshop first).

**Hints:** unchanged (get_document stays `read`).

**Tests:**
- dispatch.test: a stub whose `executeAsModal` throws turns NO_LAYER into MODAL_BUSY "crop" when the doc has a "Crop Preview" layer; a stub whose probe resolves leaves NO_LAYER as is.
- see.test: `modal` is null normally.

### A3. Placement helper (shared by every `above`)

**Files:** new `plugin/lib/place.js`, new `plugin/test/place.test.js`.

**Exports:**
- **`requireAnchor(d, id)`:** NO_LAYER if missing. Refuses an anchor whose parent chain would put the layer inside a locked or Background context: anchoring above Background is fine; anchoring below Background is never done.
- **`selectAnchor(ps, id)`:** `bp([D.selectLayerById(id)])` before a `make`, so the new layer is created directly above the anchor. This is the path add_adjustment already uses.
- **`placeAbove(ps, d, layer, anchorId)`:** after creation, if the layer is not already directly above the anchor, `layer.move(anchor, ps.constants.ElementPlacement.PLACEBEFORE)` (DOM). Then, if `layer.isClippingMask` became true while the caller didn't ask for clipping, set it to false (same rule as `stampOnTop`). Returns the layer.
- **`placeBelow(ps, d, layer, anchorId)`:** for reorder_layer `below`, using `PLACEAFTER`.
- **`isDirectlyAbove(d, layer, anchor)`:** pure sibling-index check, used to skip no-op moves.

**Behaviour notes for the descriptions:**
- An anchor inside a group puts the layer inside that group.
- An anchor that is the base of a clipping group puts the layer between the base and the clipped layers, released from the clip.

**Tests:** a stub layer tree with `move()` recording calls, covering no-op skip, PLACEBEFORE/PLACEAFTER, clip release, and a missing anchor giving NO_LAYER.

**Live check:** exercised through A8–A10.

### A6. Bug 9: render_preview region offset at integer scale

**Files:**
- new pure module `plugin/lib/preview.js` (or add to `plugin/lib/stats.js`)
- `plugin/lib/actions/see.js` (`render_preview`, `region_stats`)
- `plugin/lib/actions/edit.js` (`patchMean`)
- tests: new `plugin/test/preview.test.js`, `plugin/test/see.test.js`

**What the code does today:**
- `render_preview` clamps and rounds the region (`clampBbox`), then calls `getPixels({sourceBounds: region, targetSize: {width: maxPx}})` and reports `scale = rw / imageData.width`.
- With region 200..2250 (2050 wide) and `max_px` 1025, the ratio is exactly 2.
- The observed origin, about (94, 277) instead of (200, 450), is roughly the requested origin halved. That fits Photoshop serving an exact 2:1 read from a pyramid level and mapping `sourceBounds` into level coordinates twice. Non-integer ratios (1.54, 2.01, 2.47) were fine.
- `region_stats` (`targetSize` width 512) and `patchMean` (width 256) use the same read path, so a 1024-wide or 512-wide bbox could hit the same offset.

**Steps:**
1. **Repro (live, before the fix).**
 - Make a pixel layer with known bounds: `clone_from src_bbox:{0,0,200,200} dst:{1000,1000}` gives bounds 1000..1200.
 - `render_preview region:{left:400, top:800, right:2400, bottom:1800} max_px:1000` (ratio 2) and `max_px:999` (ratio 2.002). Find the patch's corner in each JPEG.
 - Also try ratio 3 (`max_px` 667 on a 2001-wide region; avoid exact multiples) and ratio 4, to tell "integer" from "power of two".
 - Temporarily log `getPixels`' returned `sourceBounds` and `level`. Add them to the result as `debug` for this step only.
2. **Pure `previewRequest(region, maxPx)`.** Returns `{sourceBounds, targetSize}`:
 - `targetSize` is null when the long edge ≤ maxPx.
 - Otherwise `t = maxPx`, and if `long % t === 0` (exact integer ratio ≥ 2), `t = maxPx - 1`.
 - `targetSize` is on the long side.
 - Also export `safeTargetWidth(width, cap)` for region_stats (512) and patchMean (256), using the same rule.
3. **Use it** in `render_preview`, `region_stats` and `patchMean`.
4. **After `getPixels`:** if the returned `sourceBounds` exists and differs from the request by more than 1 px, map with the returned bounds. Report them as `region`, with `scale = (returned width) / imageData.width`, and add a warning; or throw PREVIEW_MISMATCH. Pick based on step 1.
5. **Server:** no schema change. render_preview's text still reports `scale`, `preview` and `region`.

**Tests:**
- preview.test: 2050/1025 gives 1024; 2051/1025 gives 1025; 1000/1500 gives null; tall regions use height; `safeTargetWidth(1024, 512)` gives 511.
- see.test: a stub `getPixels` that returns `sourceBounds` echoes it; the integer-ratio request is never sent.

**Live check:** rerun the step 1 repro after the fix. The patch corner maps back to (1000, 1000) ±1 px at every `max_px`, and `region_stats` on bbox 1000..2024 matches stats read at full resolution.

### B1. transform_layer (item 12). No recording: `D.transform` is live-verified.

**Files:** `server/src/tools/layers.ts`, `plugin/lib/actions/layers.js`, `plugin/lib/layout.js`, tests.

- **Plugin:**
- Center comes from `layerBounds`.

- Refuse the Background and layers with null bounds.
- Returns `{layer_id, bounds}`.
- **Description:** pixel layers lose quality on repeated scaling; text, shape and smart object layers do not.
- **History:** `Claude: transform_layer, 76% 0° @ cx,cy`. **Hints:** `edit`.

**Tests:** delta math; descriptor args.

## A4 result (live, 2026-11-16): bug 1 root cause

Repro on a 449x800 JPG: `add_adjustment type:levels params:{rgb:{out_black:255,out_white:255}} above:<pixel layer>` then `mask_from_polygon` (260x8 rectangle, feather 0).
- Data is correct the whole time: `render_preview` shows the thin bar, `preview_mask` shows black with the bar, the Layers panel thumbnail shows black with the bar, History has one state per call.
- Photoshop's CANVAS shows the whole document white: the screen still displays the layer as it was before the mask write (a new adjustment layer gets an all-white mask; the levels pushes everything to white). `imaging.putLayerMask` does not invalidate the display cache. Clicking the layer row in the Layers panel retargets RGB (`select channel RGB`) but does not redraw either. The document tab reads "Bar 1, Layer Mask/8" right after the call: the mask channel is left targeted.
- `set_layer visible:false` then `visible:true` on the layer forced a redraw and the canvas showed the correct bar.
- Conclusion: bug 1 is a stale screen after an imaging-API write, plus the mask channel left targeted. What the Nov 15 user saw ("whole screen white") was the stale canvas. Treat any later all-white `render_preview` as unexplained (not reproduced; possibly a user action on the still-targeted mask channel).

A5 fix, therefore:
1. In the shared mask-write path (and after any `putPixels`): inside the same suspended step, toggle `layer.visible` off and on through the DOM (no extra history states inside suspendHistory), or an equivalent cheap redraw; then `select channel RGB` (`{_obj:"select",_target:[{_ref:"channel",_enum:"channel",_value:"RGB"}],makeVisible:false}`) so later user clicks hit pixels, not the mask.
2. `add_adjustment` deselects before `make` (an active selection would otherwise become the mask).
3. `maskEnabled` in the tree (A1) stays useful but is not the cause here.
4. `get_document` exposes nothing new for this; no `set_layer mask_enabled` needed unless cheap.
